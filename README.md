# Go Live Coding: Auth Service

Необходимо реализовать ядро сервиса аутентификации на Go. Сервис должен регистрировать пользователей, выполнять вход и возвращать данные текущего пользователя.

## Функциональные требования

### `POST /register`

Регистрирует нового пользователя.

Пример запроса:

```json
{
	"email": "user@example.com",
	"password": "strong-password"
}
```

Требования:

- проверить корректность входных данных;
- не допускать регистрацию двух пользователей с одинаковым email;
- хранить пароль только в безопасно преобразованном виде;
- не возвращать пароль или его производные в ответе;
- вернуть корректный HTTP-статус для успешного запроса, невалидных данных и уже существующего пользователя.

### `POST /login`

Аутентифицирует пользователя и выдаёт токен или идентификатор сессии.

Пример запроса:

```json
{
	"email": "user@example.com",
	"password": "strong-password"
}
```

Требования:

- проверить учётные данные;
- при успехе создать токен или сессию с ограниченным временем жизни;
- не раскрывать, существует ли пользователь с указанным email;
- вернуть корректный HTTP-статус при успешной и неуспешной аутентификации.

Пример успешного ответа:

```json
{
	"token": "..."
}
```

### `GET /me`

Возвращает данные аутентифицированного пользователя.

Требования:

- принимать токен в заголовке `Authorization: Bearer <token>`;
- отклонять отсутствующий, некорректный или просроченный токен;
- не возвращать пароль или его производные.

Пример ответа:

```json
{
	"id": 1,
	"email": "user@example.com"
}
```

Можно использовать сторонние библиотеки. Выбор HTTP-роутера, PostgreSQL-драйвера, формата токена и структуры проекта остаётся за кандидатом.

## Ожидаемое поведение

Сервис должен корректно обрабатывать как минимум следующие случаи:

- успешная регистрация;
- регистрация с некорректными данными;
- повторная регистрация того же email;
- успешный вход;
- неверный email или пароль;
- запрос `/me` с валидной авторизацией;
- запрос `/me` без авторизации или с истёкшей авторизацией;
- недоступность PostgreSQL или Redis без аварийного завершения процесса.

## Результат

В репозитории должны находиться:

- исходный код сервиса;
- необходимые миграции или SQL-схема;
- описание конфигурации и способа локального запуска;
- тесты и команда для их запуска.

Если за отведённое время реализовать всё не удаётся, приоритет следует отдать рабочему сквозному сценарию, безопасности и объяснению оставшихся решений и компромиссов.

## Реализация

### Структура

- `main.go` — подключения, сборка роутера (`http.ServeMux`) и привязка хэндлеров к роутам, graceful shutdown.
- `connections/` — `postgres.go` (pgxpool) и `redis.go` (go-redis), параметры берутся напрямую из переменных окружения.
- `handlers/` — по функции-хэндлеру на файл: `register.go`, `login.go`, `me.go` (SQL-запросы и работа с Redis прямо в них); подключения `DB`/`Redis` и структуры запросов/ответов в `model.go`; тесты в `handler_test.go`.
- `docker/` — вся инфраструктура: `Dockerfile` сервиса, `docker-compose.yml` (app + PostgreSQL + Redis), `.env` — единственное место конфигурации, `migrations/001_create_users.sql` — SQL-схема.

### Конфигурация

Все настройки — в `docker/.env`. Значений по умолчанию в коде нет: если переменная не задана, `docker compose` откажется стартовать с понятной ошибкой. Для прода достаточно заменить пароли в `.env` на реальные.

| Переменная          | Назначение                                                     |
|---------------------|----------------------------------------------------------------|
| `APP_PORT`          | порт сервиса на хосте                                          |
| `TOKEN_TTL`         | время жизни токена в секундах (`3600` = 1 час)                 |
| `POSTGRES_HOST`     | хост PostgreSQL (`postgres` — сервис в docker-compose)         |
| `POSTGRES_PORT`     | порт PostgreSQL                                                |
| `POSTGRES_USER`     | пользователь PostgreSQL                                        |
| `POSTGRES_PASSWORD` | пароль PostgreSQL                                              |
| `POSTGRES_DB`       | имя базы                                                       |
| `POSTGRES_SSLMODE`  | `disable` внутри docker-сети; `require`/`verify-full` для внешней БД |
| `REDIS_HOST`        | хост Redis (`redis` — сервис в docker-compose)                 |
| `REDIS_PORT`        | порт Redis                                                     |
| `REDIS_USER`        | пользователь Redis (`default` — владелец `requirepass`)        |
| `REDIS_PASSWORD`    | пароль Redis (`requirepass`)                                   |
| `REDIS_DB`          | номер базы Redis (`0`–`15`)                                    |

Пароли со спецсимволами (`@ : / # ? &`, пробелы) поддерживаются; `$` требует одинарных кавычек: `POSTGRES_PASSWORD='p@ss$word'`. Любую переменную можно переопределить из окружения: `APP_PORT=18080 docker compose ...`.

PostgreSQL и Redis доступны только внутри docker-сети — наружу проброшен лишь порт сервиса.

Пароли PostgreSQL и Redis применяются при первом старте. PostgreSQL сохраняет пароль в volume, поэтому после смены `POSTGRES_PASSWORD` на уже созданной базе нужно либо сменить пароль в самой БД (`ALTER USER ... PASSWORD ...`), либо пересоздать volume (`down -v`, данные будут удалены).

### Запуск

Сервис запускается только через Docker (сервис + PostgreSQL + Redis, миграция применяется при первом старте PostgreSQL):

```sh
docker compose -f docker/docker-compose.yml up -d --build
docker compose -f docker/docker-compose.yml down      # остановить; -v — удалить данные
```

```sh
curl -i -X POST localhost:8080/register -d '{"email":"user@example.com","password":"strong-password"}'
curl -i -X POST localhost:8080/login    -d '{"email":"user@example.com","password":"strong-password"}'
curl -i localhost:8080/me -H "Authorization: Bearer <token>"
```

### Тесты

```sh
go test ./...
```

Юнит-тесты не требуют PostgreSQL и Redis: они проверяют валидацию, отказ в авторизации и ответ 503 при недоступных бэкендах. Сквозной сценарий проверяется на docker-стеке командами `curl` выше.

### Формат ответов

Все эндпоинты отвечают в едином формате `{"success": bool, "data": ..., "error": "..."}`. `/register` и `/login` кладут в `data` токен (`{"token": "..."}`), `/me` — `{"id": 1, "email": "..."}`.

### Коды ответов

| Эндпоинт         | Успех | Ошибки                                                                 |
|------------------|-------|------------------------------------------------------------------------|
| `POST /register` | 201   | 400 — невалидные данные, 409 — email занят, 503 — БД недоступна        |
| `POST /login`    | 200   | 400 — пустые поля/битый JSON, 401 — неверные данные, 503 — БД/Redis недоступны |
| `GET /me`        | 200   | 401 — нет/неверный/истёкший токен, 503 — БД/Redis недоступны           |

### Решения и компромиссы

- **Пароли** хэшируются bcrypt (cost по умолчанию). Длина пароля 8–72 байта: bcrypt игнорирует всё после 72 байт.
- **Токен** — 32 случайных байта (base64url), непрозрачный. В Redis хранится `session:<sha256(token)>` → `user_id` с TTL, поэтому истечение обеспечивает сам Redis, а утечка дампа Redis не даёт рабочих токенов. Непрозрачный токен выбран вместо JWT, чтобы сессию можно было отозвать удалением ключа.
- **Уникальность email** обеспечивает UNIQUE-индекс (код ошибки `23505` → 409), а не SELECT перед INSERT — нет гонки. Email приводится к нижнему регистру.
- **Перечисление пользователей**: `/login` отвечает одинаково (401, одно сообщение) для неизвестного email и неверного пароля. Защиты от timing-атаки (сравнение с фиктивным хэшем) нет — осознанное упрощение. `/register` при этом по требованию возвращает 409, то есть существование email через регистрацию выяснить можно — это заложено в ТЗ; защищаться стоит rate limiting'ом.
- **Недоступность PostgreSQL/Redis**: подключения ленивые, процесс стартует без них; запросы получают 503 с таймаутом 3 с на операцию и продолжают работать после восстановления.
- **Не сделано**: rate limiting на `/login` и `/register`, logout/отзыв токенов, запуск миграций из приложения (сейчас — через `docker-entrypoint-initdb.d` или вручную `psql -f docker/migrations/001_create_users.sql`), интеграционные тесты с настоящими PostgreSQL и Redis (например, testcontainers).
